Cursor / Claude Code 在国内用不了模型？按这个顺序查

2026-11-17 · 海桥 · 排查耗时按顺序递增，前两步就能解决大多数

先给结论：这类问题九成不是"网络坏了"，而是三层配置里的某一层没对上。按下面顺序查，每步都有明确的判据。

第一层：客户端有没有真的拿到 key

最容易踩的坑：你在系统里设了环境变量，但客户端进程根本读不到。GUI 程序经常不继承你终端里的变量。

curl -H "Authorization: Bearer $KEY" $BASE/chat/completions \
  -d '{"model":"...","messages":[{"role":"user","content":"hi"}]}'

curl 通了 → 问题在客户端；curl 也不通 → 问题在 key 或地址。这一条能省掉一半时间。

第二层：模型名对不对

Model not available、404 这类，八成是名字不匹配。各家对同一模型的写法不一样，本地 ollama 更是——ollama list 里显示什么就得写什么，不能照抄教程。

两个动作：① 请求一次 /models 看服务端认哪些名字；② 把返回的 id 原样填回去。

第三层：Base URL 的三个细节

细节错误表现
末尾多一个斜杠404 或 401，容易误判成 key 问题
该不该带 /v1带错报 404，不报"地址错"
http 还是 https本地服务写 https 会直接连不上

都不是？还有一层：协议协商

Cursor / Claude Code 里有个隐藏坑：HTTP/2 协商失败会表现为"请求发出去了但没回"，超时报错里看不出任何线索。把客户端设置里的 HTTP Compatibility Mode 切到 1.1 再试一次，很多人这一步就好了。

为什么反复出现：客户端绑死了模型

上面每一步都是"客户端 ↔ 模型"之间的对接细节。只要你的客户端绑死某一家，每次换模型、每次对方改区域策略，这些细节就要重来一遍。

稳的做法是把模型层抽出来：客户端只认一个 OpenAI 兼容入口，背后接哪家随时换。这就是我做 mcp-bridge 的原因——它是 MCP 服务，把 DeepSeek / 通义 / 智谱 / Kimi 与本地 ollama 收成一个入口，客户端只配一次；每次调用落本地账本，能按项目分账；上游不通时回落本机模型，并在回执里标注降级。
